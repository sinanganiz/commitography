# M1 — Release and Distribution

**Depends on:** M0. **Blocks:** M5 (the composite Action downloads a published release asset).
**Closes:** Phase 1 exit criterion 11; Phase 2 exit criteria 1 and 2.

[`.goreleaser.yml`](../../.goreleaser.yml) is fully written and has **never been executed**. It defines twelve build targets, GHCR images for two architectures with a multi-arch manifest, a Homebrew formula and a Scoop manifest. M1 does not design any of that. M1 installs the tool, validates the configuration, creates the two repositories it writes to, and runs it once.

Because the project's own CI was declined (decision A2), every step here runs from the development machine. That is a deliberate constraint and shapes two packages: WP-1.1 validates configuration that CI would otherwise have caught, and WP-1.3 has a documented fallback for the one step that a Windows host may not be able to perform.

## WP-1.1 — Install goreleaser and validate the configuration

Phase 1 recorded that `goreleaser check` has never been run and that the `{{ if ne .Os "darwin" }}` ldflag template is therefore unvalidated. That template exists because of a defect that made every macOS binary refuse to start. An unvalidated fix for that class of defect is the first thing to resolve.

### Steps

1. Install goreleaser on the development machine. Record the exact version in this file when the package is completed; every later measurement and artifact is tied to it.
2. Run `goreleaser check`. It MUST exit 0. If the darwin ldflag template is rejected, fix it and record what was wrong — Phase 1 flagged it as unvalidated precisely because this outcome was possible.
3. Run `goreleaser build --snapshot --clean --single-target` and confirm a binary is produced.
4. Run `goreleaser build --snapshot --clean` to build all twelve targets, and confirm all twelve appear under `dist/`.

### Configuration edits

The following MUST be added to [`.goreleaser.yml`](../../.goreleaser.yml) as part of this package.

**1. Pre-release detection.** WP-1.3 publishes a pre-release, because Phase 1 criterion 1 is not met. Add:

```yaml
release:
  prerelease: auto
```

`auto` marks the GitHub release as a pre-release when the tag carries a semver pre-release suffix, and as stable otherwise. This means the first stable release requires only dropping the suffix from the tag, with no configuration change and therefore no opportunity to forget.

**2. Nothing else.** The build, archive, checksum, docker, brew and scoop sections are correct as written and MUST NOT be redesigned in this package. If `goreleaser check` reports a problem, fix that problem only.

### Verification of the darwin binary

`goreleaser build --snapshot --clean` produces a darwin binary that cannot be executed here. What CAN be checked from Windows, and MUST be:

- The darwin/arm64 and darwin/amd64 binaries are Mach-O files.
- Both carry an `LC_UUID` load command.

Phase 1 established that a cross-compiled `CGO_ENABLED=0` darwin binary carries `LC_UUID` even when stripped, and that the observed failure belonged to the cgo-enabled path on a macOS host. This check therefore confirms the artifact is well-formed; it does **not** confirm that macOS runs it. Phase 1 criterion 1 stays open regardless of the outcome, and this package MUST NOT be written up as though it closes it.

### Acceptance criteria

- `goreleaser check` exits 0, and the goreleaser version is recorded in this file.
- Twelve binaries build from a clean tree.
- Both darwin binaries are Mach-O and carry `LC_UUID`.
- `release.prerelease: auto` is present in `.goreleaser.yml`.

## WP-1.2 — Create the tap and bucket repositories

[`.goreleaser.yml`](../../.goreleaser.yml) writes a Homebrew formula to `sinanganiz/homebrew-tap` and a Scoop manifest to `sinanganiz/scoop-bucket`, authenticating with `TAP_GITHUB_TOKEN`. Neither repository exists.

### Steps

1. Create the public repository `sinanganiz/homebrew-tap`. Homebrew requires the `homebrew-` name prefix; `brew install sinanganiz/tap/commitography` resolves to it by convention.
2. Create the public repository `sinanganiz/scoop-bucket`.
3. Both repositories MUST contain at minimum a `README.md` stating what they are, that their contents are generated by goreleaser, and that pull requests against generated files will be closed. An empty repository invites a well-meaning contributor to hand-edit a file that the next release overwrites.
4. Create a fine-grained personal access token with contents write access to those two repositories **and no others**. It MUST NOT have access to the main project repository: goreleaser uses `GITHUB_TOKEN` for the release itself and `TAP_GITHUB_TOKEN` only for the tap and bucket, so a narrower token is sufficient and a wider one is an unnecessary standing risk.
5. Store the token so that WP-1.3 can supply it as the `TAP_GITHUB_TOKEN` environment variable. It MUST NOT be written into any file in the project repository, including a `.env` that `.gitignore` happens to cover.

### Acceptance criteria

- Both repositories exist, are public, and carry the stated README.
- A token exists whose scope is exactly those two repositories.
- `git grep -iE "ghp_|github_pat_"` over the project repository returns nothing.

## WP-1.3 — Tag and publish the first pre-release

### Preconditions

All MUST hold before tagging:

- WP-1.1 and WP-1.2 are complete.
- `go vet ./...` is clean and `gofmt -l cmd internal` is empty.
- `go test ./...` passes.
- The working tree is clean and `main` is pushed.
- The frontend bundle under `internal/render/assets/` is current: run the frontend build and confirm `git status` reports no change to `app.js` or `app.css`. A stale committed bundle would ship a release whose dashboard does not match its source, and nothing else in the pipeline would notice.

### Steps

1. Tag `v0.1.0-rc.1`. The pre-release suffix is required: Phase 1 exit criterion 1 is not met, macOS binaries are being published unverified, and `release.prerelease: auto` turns the suffix into a visible pre-release marker on the release page.
2. Export `GITHUB_TOKEN` and `TAP_GITHUB_TOKEN`.
3. Authenticate to GHCR with a token carrying `write:packages`.
4. Run `goreleaser release --clean`.

### The multi-arch image is the fragile step

`.goreleaser.yml` builds `linux/arm64` images with buildx from a machine that is not arm64. This requires QEMU emulation to be registered with the Docker daemon. On a Windows host with Docker Desktop this usually works and may silently not.

**Normative rule:** if the arm64 image build fails, the release MUST NOT be abandoned or forced. Re-run with `--skip=docker`, publish the archives, formula and manifest, and record the image as outstanding. The container image is Phase 2 deliverable 5 and blocks Phase 2 exit criterion 1, but it blocks nothing in M5 — the composite Action downloads a release archive (decision C2), not an image. Publishing the images from a Linux host or WSL afterwards is a valid completion of this package.

Under no circumstances may `docker_manifests` be edited to drop arm64 in order to make the command succeed. An amd64-only image published under a multi-arch manifest name is worse than no image.

### Acceptance criteria

- A GitHub release for `v0.1.0-rc.1` exists, marked as a pre-release.
- It carries twelve archives and `commitography_v0.1.0-rc.1_checksums.txt`.
- Each archive contains the binary, `README.md`, `LICENSE` and `docs/report-schema.json`.
- `sinanganiz/homebrew-tap` and `sinanganiz/scoop-bucket` each received a generated file.
- Either the multi-arch image is pullable on both architectures, or its absence is recorded here with the reason.

## WP-1.4 — Verify installation from both package managers

Phase 1 exit criterion 11 requires the binary to be installable from two package managers. Installing it is the verification; nothing short of that counts.

### Steps

1. On Windows: `scoop bucket add sinanganiz https://github.com/sinanganiz/scoop-bucket` then `scoop install commitography`. Run `commitography --version` and confirm it prints the tagged version, the correct commit, and a build date — not `dev`/`unknown`, which would mean the ldflags did not reach the binary.
2. On Linux: `brew install sinanganiz/tap/commitography`, then the same `--version` check. Homebrew on Linux is sufficient to demonstrate the formula resolves and installs; the formula's own `test` block runs `--version` as well.
3. Run the installed binary against a real repository end to end and confirm it produces a dashboard.

### What this does not verify

Homebrew on macOS is where most Homebrew users are, and it is not covered. The formula is verified to resolve and install; the binary it installs on macOS is the same unverified darwin artifact that Phase 1 criterion 1 is about. This limitation MUST be stated wherever the criterion is marked met.

### Acceptance criteria

- Both package managers install a binary that answers `--version` with the tagged version.
- The installed binary produces a dashboard from a real repository.
- Phase 1 exit criterion 11 is marked met in [`phase-1-detailed.md`](../phase-1-detailed.md), with the macOS limitation stated alongside it.

## WP-1.5 — Verify the container image

Skip this package if WP-1.3 recorded the image as outstanding; complete it when the image is published.

### Steps

1. `docker pull ghcr.io/sinanganiz/commitography:v0.1.0-rc.1` on amd64, and on arm64 if a host is available. Confirm the manifest resolves per architecture rather than serving one image to both.
2. Run the image against a mounted repository:
   ```
   docker run --rm -v /path/to/repo:/repo ghcr.io/sinanganiz/commitography:v0.1.0-rc.1
   ```
   With no arguments this uses the Dockerfile's `CMD` of `/repo -o /repo/out`. Confirm `out/index.html` appears in the mounted directory.
3. Confirm the `git config --global --add safe.directory '*'` line in the [`Dockerfile`](../../Dockerfile) does its job: the mounted repository is owned by a different uid than the container user in the normal case, and git refuses to read such a repository without it. Verify by mounting a repository owned by a different uid, not by reading the Dockerfile.
4. Confirm the image contains `git` and that `commitography --version` inside it reports the tagged version.
5. Record the compressed image size. It is a CI job image; if it exceeds roughly 50 MB, note it as something for M8 to look at rather than fixing it here.

### Acceptance criteria

- The image runs and produces a dashboard from a mounted repository owned by a different uid.
- The multi-arch manifest resolves correctly on each architecture tested, and any untested architecture is named.
- `--version` inside the image matches the tag.
